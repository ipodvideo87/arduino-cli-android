# Native Android USB Upload Milestone

## Milestone

Define and validate a reusable native Android USB serial upload and monitor
architecture.

ESP32-S3 is the first proof device, not the only target.

This milestone is planning and research until the new implementation is proven
on-device.

## Current State

- Native Termux compilation of Blink is validated on-device.
- Native Termux compilation of a larger multi-file ESP32-S3 project is reported
  as successful in this workstream.
- Firmware generated by the current build is reported as valid in this workstream
  because it was flashed from an Android application and booted the expected web
  server behavior.
- Android USB host access is demonstrably possible on this hardware.
- Termux USB permission flow works, but acquisition latency and intermittent
  failures still need explanation.
- The reusable ACL USB serial bridge is not implemented end-to-end yet.
- Successful compiles now emit a stable firmware package, build manifest, flash
  plan, and validation report.
- Platform and tool installs now flow through the shared Android patch pipeline.
- Compatibility decisions now feed into library and platform selection paths.

## Why This Milestone Exists

The compile milestone proved that the toolchain and patching work on native
Android.

Upload and serial monitor are a separate problem because Android USB access is
app-scoped and does not behave like a desktop `/dev/ttyUSB*` or `/dev/ttyACM*`
path.

The transport must therefore be generic:

- discovery
- permission
- descriptor parsing
- connection management
- PTY export or RFC2217 fallback

## Architecture Decision

The upload path should be transport-based, not board-specific.

Planned transport choices:

1. Use a normal serial port when a usable `/dev/tty*` path already exists.
2. Use a Termux-native USB file-descriptor path when Termux can acquire the
   device directly.
3. Use an Android USB host bridge when permission or device handling requires
   Android host APIs.

The bridge should expose a generic serial endpoint to the rest of the toolchain.

## Android Post-Install Pipeline

Every installed platform or tool should automatically pass through:

`Download -> Extract -> Android Patch -> Permission / Runtime Fixes -> Executable Validation -> Toolchain Registration -> Self-Test -> Ready`

The pipeline should be shared and automatic.

It should not be repeated manually by the user.

## Validation Plan

The milestone will not be marked complete until the following are proven on the
real Android device with the new implementation:

1. Detect the target USB device.
2. Obtain the required Android USB permission or equivalent native fd.
3. Open the USB connection.
4. Identify the serial-capable interface and endpoints.
5. Expose a stable serial endpoint to the toolchain.
6. Run an `esptool` chip-identification probe through the bridge.
7. Flash a firmware package.
8. Confirm serial monitor output after upload.

## Remaining Work

- Implement the reusable ACL USB serial bridge.
- Decide whether the first bridge backend is Termux-native fd handoff or Android
  `UsbManager`.
- Add automatic Android post-install processing to the package install path.
- Add regression tests for the selected transport layer.
- Validate upload and serial monitor on native Android hardware.

## Open Questions

- Can Termux-native USB acquisition be made reliable enough on the target device?
- Does the device path change after permission is granted?
- Does the bridge need PTY only, or PTY plus RFC2217?
- Which install entry points should invoke Android post-processing first?
- Which diagnostics are required before the bridge can be trusted for upload?
